# Feast Feature Store — Design Spec

**Date:** 2026-05-03  
**Status:** Approved  
**Scope:** Feast feature repository, offline (file/MinIO) + online (Redis) stores, materialization script, Airflow wiring, docs update.

---

## 1. Problem

The Gold layer now produces three Delta tables nightly:

| Table | Path | Key |
|---|---|---|
| `fraud_detection_ml_features` | `s3a://gold/fraud_detection_ml_features` | `transaction_id` |
| `customer_features` | `s3a://gold/customer_features` | `customer_id` |
| `terminal_features` | `s3a://gold/terminal_features` | `terminal_id` |

Without a feature store:
- ML team reads raw Delta files manually — no point-in-time join semantics, no versioning.
- KServe transformer has no standardised way to look up customer/terminal features at serving time.

Feast solves both: **offline** for training dataset retrieval, **online** for <10 ms Redis lookups during inference.

---

## 2. Offline Store Decision: File (MinIO) instead of PostgreSQL

The architecture document originally listed PostgreSQL as the Feast offline store.  
**This spec changes that to a file-based offline store backed by MinIO.**

**Rationale:**
- Delta tables on MinIO are already the source of truth for Gold features. Copying them into a second relational store adds an extra pipeline step and a sync problem.
- Feast `FileSource` reads the Parquet data files that Delta Lake writes inside the table directory. The `_delta_log/` folder is ignored. This works correctly for read-only historical retrieval.
- PostgreSQL offline store is retained for MLflow and Airflow metadata; removing it from Feast avoids adding a third schema to that instance.
- For a local/dev setup, file source is simpler to operate. If a large-scale multi-user feature store is needed later, migrating to BigQuery or Redshift offline store is a configuration change.

**Docs to update:** `docs/architecture.md` Feature Store section.

## 3. Repository Layout

```
src/feast/
  feature_store.yaml            — registry, offline (file), online (Redis)
  entities.py                   — Transaction, Customer, Terminal entities
  feature_views/
    __init__.py
    fraud_ml_features.py        — FraudMLFeaturesView  (offline-only, entity: transaction_id)
    customer_features.py        — CustomerFeaturesView (offline+online, entity: customer_id)
    terminal_features.py        — TerminalFeaturesView (offline+online, entity: terminal_id)
  materialize_to_redis.py       — standalone script: materialize Customer + Terminal → Redis
```

---

## 4. `feature_store.yaml`

```yaml
project: fraud_detection
registry: data/feast_registry.db
provider: local
offline_store:
  type: file
online_store:
  type: redis
  connection_string: "redis:6379"
entity_key_serialization_version: 2
```

- Registry is a local SQLite file at `data/feast_registry.db` (committed to `.gitignore`, regenerated by `feast apply`).
- `connection_string` is read from env var `FEAST_REDIS_CONNECTION_STRING` in production; the yaml default targets Docker Compose Redis service name.

## 6. Feature Views

### 6.1 `FraudMLFeaturesView` — Offline only (training dataset)

**Source:** `s3a://gold/fraud_detection_ml_features/`  
**Entity:** `transaction_id`  
**`event_timestamp_column`:** `event_timestamp` (Feast point-in-time join key from Silver)  
**TTL:** 365 days  
**Features (17):**

| Feature | Type | Description |
|---|---|---|
| `TX_AMOUNT` | Float64 | Transaction amount |
| `IS_WEEKEND` | Bool | Weekend flag |
| `IS_NIGHT` | Bool | Night flag |
| `CUSTOMER_AVG_AMOUNT_WINDOW_1D` | Float64 | |
| `CUSTOMER_AVG_AMOUNT_WINDOW_7D` | Float64 | |
| `CUSTOMER_AVG_AMOUNT_WINDOW_30D` | Float64 | |
| `CUSTOMER_NUMBER_OF_TRANSACTIONS_WINDOW_1D` | Int64 | |
| `CUSTOMER_NUMBER_OF_TRANSACTIONS_WINDOW_7D` | Int64 | |
| `CUSTOMER_NUMBER_OF_TRANSACTIONS_WINDOW_30D` | Int64 | |
| `TERMINAL_RISK_1DAY_WINDOW` | Float64 | |
| `TERMINAL_RISK_7DAY_WINDOW` | Float64 | |
| `TERMINAL_RISK_30DAY_WINDOW` | Float64 | |
| `TERMINAL_NB_TX_1DAY_WINDOW` | Int64 | |
| `TERMINAL_NB_TX_7DAY_WINDOW` | Int64 | |
| `TERMINAL_NB_TX_30DAY_WINDOW` | Int64 | |
| `TX_FRAUD` | Int64 | Label (0/1) |
| `feature_date` | — | partition column (not a Feast feature) |

Usage:
```python
store.get_historical_features(
    entity_df=entity_df,  # columns: transaction_id, event_timestamp
    features=["fraud_ml_features_view:TX_AMOUNT", ...]
).to_df()
```

### 6.2 `CustomerFeaturesView` — Offline + Online

**Source:** `s3a://gold/customer_features/`  
**Entity:** `customer_id`  
**`event_timestamp_column`:** `event_timestamp` (or `feature_date` promoted to timestamp)  
**TTL:** 2 days  
**Features (6):** `CUSTOMER_AVG_AMOUNT_WINDOW_1D/7D/30D`, `CUSTOMER_NUMBER_OF_TRANSACTIONS_WINDOW_1D/7D/30D`

Materialized to Redis. KServe transformer looks up by `customer_id` at inference time.

### 6.3 `TerminalFeaturesView` — Offline + Online

**Source:** `s3a://gold/terminal_features/`  
**Entity:** `terminal_id`  
**TTL:** 2 days  
**Features (6):** `TERMINAL_RISK_1DAY/7DAY/30DAY_WINDOW`, `TERMINAL_NB_TX_1DAY/7DAY/30DAY_WINDOW`

Materialized to Redis. KServe transformer looks up by `terminal_id` at inference time.

## 7. Materialization Script

**File:** `src/feast/materialize_to_redis.py`

```
feast apply                                     # sync registry
feast materialize-incremental <end_date>        # push customer + terminal → Redis
```

Or via Python SDK:
```python
store = FeatureStore(repo_path="src/feast")
store.materialize_incremental(end_date=datetime.utcnow())
```

The script:
1. Loads `feature_store.yaml` from `src/feast/`
2. Calls `store.materialize_incremental(end_date=now)` scoped to `CustomerFeaturesView` and `TerminalFeaturesView` only (`FraudMLFeaturesView` is never pushed online)
3. Prints summary and exits with 0 on success

## 8. Airflow DAG Update

New task `materialize_online_features` added to `feature_pipeline_daily.py`:

```
assemble_ml_features >> materialize_online_features
```

Implemented as a `BashOperator` running:
```bash
python src/feast/materialize_to_redis.py
```

or via `DockerOperator` if feast is not installed in the Airflow worker image.
